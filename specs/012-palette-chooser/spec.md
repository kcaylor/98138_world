# Feature Specification: Palette chooser and ice toggle on the map pages

**Feature Branch**: `012-palette-chooser`

**Created**: 2026-11-22

**Status**: Implemented (owner decisions relayed by the coordinating agent and recorded as (user);
agent decisions logged in `run-state.md` for owner review)

**Input**: Owner request, relayed by the coordinating agent on 2026-11-22: "Improve the app to
allow users to change color schemes for each of the maps, as we have developed within Claude
Desktop as part of the Palette Chooser. Each map should allow for this, but we won't re-price or
alter the instructions, etc. for now. I just want that functionality to play around with in the
app and see how the maps look with different color selections and bins. I want it to be like the
Color Selector we already have. In addition, add a toggle to allow either sea ice or ice-covered
regions to contain map data (or not). For example, rainfall over Antarctica, or chlorophyll under
polar sea ice."

Design reference: the owner's two Palette Chooser pages (saved HTML, outside the repository;
summarised in `research.md` R1). No color selector exists in this repository (research R1).

## Context

The site (feature 008) shows six bundled maps in combinations A, B and C, each as a stud preview
built ahead of time by the CLI library, with build files, parts lists and (feature 011) price
estimates. A visitor cannot see how a map would look in other colors or with other class bounds.
This feature adds an exploration tool on each map page: recolor each layer, change the number of
classes and their bounds, see each class's share of studs, and choose whether ice-covered regions
show the map's data or White ice. It is a preview only: it never changes the parts lists, prices,
build sheets or downloads.

Constitution principle VI applies: the per-cell values and classes the browser recolors are
computed by the CLI library (a library function and a CLI command), written by the prebuild as a
static file, and only recolored in the browser.

## Clarifications

### Session 2026-11-22 (owner decisions, relayed by the coordinating agent)

- Q: May map pages use JavaScript? → A: Map pages must still work fully without JavaScript. A small
  hand-written script, served from the site's own static files (no third-party loads, no cookies,
  no trackers, no front-end build), adds live recoloring and bin editing as progressive
  enhancement. Feature 008's FR-009 is amended accordingly by this feature (FR-020 below); 008
  documents and tests that assert "no JavaScript" now assert "works without JavaScript; only a
  first-party script". (user)
- Q: Does the chooser change the parts lists, prices, build sheets or downloads? → A: No.
  Exploration and preview only; nothing downloadable or priced is recomputed. The page says so
  plainly: "Preview only: parts lists, prices, build sheets and downloads use the map's default
  colors." (user)
- Q: Disclaimer? → A: Every user-facing surface keeps "Not affiliated with or endorsed by The LEGO
  Group." (user)

### Session 2026-11-22 (autonomous clarify)

- Q: Which colors may a visitor choose? → A: Only colors in the cited part-color table
  (`part_colors.json`): land classes from the 1×1 round plate (6141, 44 colors), ocean classes and
  the land shadow from the 1×1 round tile (98138, 40 colors). Kit 31203 colors are marked. Each
  color is shown with its BrickLink name, LEGO name and CIE L* (lightness from the cited sRGB),
  sorted light to dark, as in the Palette Chooser. (auto-resolved: constitution V; research R1)
- Q: What is editable per map? → A: Per layer, by role and classification (research R3):
  data layers with `bins`, `rank`, `rank-to-supply` or `quantile` classification: colors, number
  of classes (1–12) and class bounds in the data's units; `categorical` (the official design's
  ocean): colors per category only; background layers: the color of each background class (one
  color for white land, base and coast-ring colors for the halo ocean). The land shadow color is
  editable where the map has a shadow. (agent decision: follows the recipe model, feature 004)
- Q: What does the default chooser state show? → A: Exactly the built map: each cell's class as
  built (including the blend texture) in the recipe's colors, so the default equals the prebuilt
  preview. Changing only colors keeps the built classes. Changing the number of classes or any
  bound switches that layer to plain bins on the cell values (no blend texture), and the page says
  so. For rank-based layers the starting bounds are the value boundaries between the built classes.
  (agent decision: the preview must stay the default rendering; research R4)
- Q: Where do the ice regions come from? → A: A packaged, cited reference file,
  `kit_31203_ice.json`, regenerated by a maintainer tool with `--check`: land ice is Antarctica
  (land cells whose centre lies south of 60° S) and Greenland (land cells with centre latitude ≥ 59°
  and longitude −75° to −10°, excluding Iceland: latitude ≤ 67° and longitude ≥ −26°), the same
  regions as the unmerged `013-rainfall` design; sea ice is the ocean cells whose 1991–2020 warmest-
  month mean sea surface temperature (NOAA ERSST v5 long-term monthly means, the pinned
  `ersst-v5-ltm-1991-2020` file) is at or below −1.5 °C (near freezing all year), or that have no
  ERSST value and lie poleward of 60°. (agent decision: no new dataset; research R5. CLOSE CALL,
  FOR OWNER REVIEW: the `013-rainfall` branch pins an NSIDC sea-ice climatology that could replace
  the sea-ice rule when merged.)
- Q: What does the ice toggle do? → A: One toggle per map page, "Ice-covered regions": "show the
  map's data" (default, equal to the built map) or "show as White ice" (every land-ice and sea-ice
  cell White, plate or tile as the layer requires; White is cited for both parts). The land shadow
  keeps its color in both states. Class shares are computed over the cells that show data.
  (agent decision: the default must equal the prebuilt preview; no current map paints ice White)
- Q: What happens to ice cells where the dataset has no value? → A: The build gives a cell with no
  source value the value of the nearest cell with one (feature 004, FR-014), and the chooser shows
  that value in "show the map's data", exactly as the build does. The page states how many cells of
  each layer have no source value and how many of them lie in ice regions, so the visitor knows
  where the data is filled. Per map (research R6): `land-elevation` has elevation under the ice
  sheets (ice-surface heights); `ocean-sst` and the ENSO maps have no ERSST value in the
  permanently frozen Arctic Ocean (filled from the nearest value); `official-31203-bathymetry` has
  depth under sea ice; `official-31203` (the design itself) has a design color under sea ice.
  (agent decision: matches the build; CLOSE CALL, FOR OWNER REVIEW: alternative is to show those
  cells White even in "show the map's data")
- Q: Can a palette be shared? → A: Yes, in the URL fragment (`#palette=…`), which is never sent to
  the server; no cookies and no browser storage. Opening such a link restores the choices when they
  are valid for that map and are otherwise ignored with a message. (agent decision: no new
  privacy surface)
- Q: How are the values delivered? → A: One static JSON file per variant (`cells.json`), written
  by the prebuild with the CLI library and listed in `manifest.json` with size and SHA-256, served
  at `/maps/<map>/<C>/cells.json`. The CLI command `map cells RECIPE -o FILE` writes the same file.
  (agent decision: constitution VI)

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Recolor a map (Priority: P1)

A visitor on a map page opens "Try other colors", picks a different color for a class of the land
or ocean layer from the colors that part is made in, and sees the preview update at once, with a
legend that shows each class's range, color names, lightness and share of studs.

**Why this priority**: it is the core of the request and is useful on its own.

**Independent Test**: on any map page with JavaScript, change one class color; the preview changes
those studs only; reset restores the built preview. Without JavaScript the page is unchanged from
feature 008 apart from a note that the chooser needs JavaScript.

**Acceptance Scenarios**:

1. **Given** a map page with JavaScript, **When** it loads, **Then** the chooser shows, per layer,
   one row per class with a stud swatch, the class range (data layers) or role (background), the
   BrickLink and LEGO color names, L*, and the share of the layer's studs; the preview is the built
   image.
2. **Given** the chooser, **When** the visitor picks another color for a class, **Then** the
   preview shows that color on every stud of the class and the legend updates; the picker offers
   only the colors cited for that layer's part, sorted light to dark, with kit colors marked.
3. **Given** a changed palette, **When** the visitor presses "Reset to the map's colors", **Then**
   the preview equals the built preview again.
4. **Given** any chooser state, **When** the page is shown, **Then** it says "Preview only: parts
   lists, prices, build sheets and downloads use the map's default colors." and the footer
   disclaimer is present.
5. **Given** JavaScript is off, **When** a map page loads, **Then** every feature 008/011 element
   works as before and a note says the color chooser needs JavaScript.

---

### User Story 2 - Change the classes and bounds (Priority: P1)

The visitor changes the number of classes of a data layer and edits the class bounds in the data's
units (for example metres of elevation, °C of sea surface temperature), and sees the preview and
class shares update.

**Why this priority**: the owner asked for "different color selections and bins".

**Independent Test**: on `land-elevation`, set 5 classes and edit one bound; the share column sums
to 100%, each stud's class follows its value, and the page notes that custom bounds are plain bins
without the blend texture.

**Acceptance Scenarios**:

1. **Given** a data layer with bins (`land-elevation` land, the ENSO oceans), **When** the chooser
   opens, **Then** the bounds shown are the recipe's bounds.
2. **Given** a rank-based data layer (`ocean-sst`, `official-31203-bathymetry` ocean), **When**
   the chooser opens, **Then** the bounds shown are the value boundaries between the built classes.
3. **Given** a new number of classes, **When** it is applied, **Then** the bounds are reset to
   equal-share bounds on the layer's values and the colors are spread along the current ramp; every
   class can then be recolored.
4. **Given** bounds that are not strictly increasing or not numbers, **When** entered, **Then**
   the chooser refuses them with a message next to the field and keeps the last valid state.
5. **Given** a categorical or background layer, **When** the chooser opens, **Then** it offers
   colors only and says why bounds do not apply.

---

### User Story 3 - Ice-covered regions (Priority: P2)

The visitor switches ice-covered regions (the Antarctic and Greenland ice sheets on land, polar
sea ice in the ocean) between showing the map's data and showing White ice.

**Why this priority**: requested, but secondary to recoloring.

**Independent Test**: on `land-elevation`, switch to White ice: the Antarctica and Greenland studs
turn White and the land class shares are recomputed without them; switch back: the preview equals
the built one.

**Acceptance Scenarios**:

1. **Given** any map page, **When** the chooser opens, **Then** the toggle shows "show the map's
   data" selected and the preview equals the built preview.
2. **Given** "show as White ice", **When** applied, **Then** every land-ice and sea-ice stud is
   White, the land shadow keeps its color, and class shares exclude ice studs.
3. **Given** a map whose dataset has no value under some ice studs, **When** the chooser opens,
   **Then** it states how many studs have no source value, how many of those are ice, and that
   they show the nearest value as in the build.
4. **Given** the toggle, **When** read by assistive technology, **Then** both options are labelled
   radio buttons in a fieldset with a legend.

---

### User Story 4 - Share a palette (Priority: P3)

The visitor copies the page address after choosing colors and sends it; opening it shows the same
choices.

**Independent Test**: choose colors and bounds; reload the page with the same address; the chooser
restores them. An address with an unknown color or a bad bound is ignored with a message.

**Acceptance Scenarios**:

1. **Given** a changed palette, **When** the state changes, **Then** the address fragment encodes
   it and no request, cookie or storage write is made.
2. **Given** a fragment for a different map or with invalid content, **When** the page opens,
   **Then** the default state is shown with a short message.

### Edge Cases

- A map variant without `cells.json` (an output built before this feature): the chooser is not
  offered and the page is otherwise unchanged.
- `cells.json` fails to load or is malformed: the chooser shows "The color chooser could not load"
  and the built preview stays.
- One class: allowed; the layer is one color.
- More than 12 classes: refused (the input's maximum is 12).
- A class with no studs: listed with 0%.
- Ice toggle on a map whose land is already White (`official-31203`, the ocean maps): land does not
  change; sea ice in the ocean turns White. The chooser says which layers the toggle affects.
- The land shadow lies on ocean cells; in "show as White ice" it keeps its color.
- Phone width (360 px): controls stack in one column with no horizontal page scrolling.

## Requirements *(mandatory)*

### Functional Requirements

**CLI library and command (CLI first)**

- **FR-001**: The library MUST provide a function that, from a built map, returns the per-cell
  data the chooser needs for the board as hung: for each layer its role, part, classification
  method, texture kind, recipe colors, each cell's class as built, and for data layers each cell's
  value (in the recipe's units after any transform), the cells with no source value, the units,
  the value range and default class bounds (recipe bounds for `bins`, boundaries between built
  classes for rank methods); the categories of a categorical layer; the land shadow's cells and
  color; the land-ice and sea-ice cells; and the cited colors of each part with BrickLink and LEGO
  names and IDs, sRGB, kit membership and CIE L*.
- **FR-002**: The CLI MUST offer `map cells RECIPE -o FILE [--arrangement A|B|C] [--cache-dir]`
  writing that data as JSON (format version "1"), printing a short summary and the disclaimer; it
  never downloads data and fails like `map build` when a dataset is not cached.
- **FR-003**: The ice regions MUST come from packaged reference data
  (`data/kit_31203_ice.json`) with a `source` block citing the rules and the pinned ERSST v5 file
  (URL, SHA-256), in kit (A) coordinates, rolled to the board as hung; a maintainer tool MUST
  regenerate it and check it (`--check`: exit 0 and "no differences" when reproducible).
- **FR-004**: The file MUST NOT change any layout, parts list, price, sheet or report: building a
  map with or without writing it gives byte-identical layouts.
- **FR-005**: The file MUST carry the disclaimer and the preview-only note.

**Prebuild and service**

- **FR-006**: The prebuild MUST write `cells.json` for every variant with the library function and
  list it in `manifest.json` (kind `cells`, size, SHA-256, media type `application/json`).
- **FR-007**: The service MUST serve `cells.json` at `/maps/<map>/<C>/cells.json` from the built
  output only (validated against the manifest, not as a download attachment) and MUST NOT import
  `lego_image_processor`.
- **FR-008**: The service MUST serve the chooser script from its own static files
  (`/static/palette.js`) and the content security policy MUST allow scripts and fetches from the
  site itself only (`script-src 'self'; connect-src 'self'`), with no inline script.

**Map page and chooser**

- **FR-009**: Each map page whose variant has `cells.json` MUST include the chooser markup, hidden
  until the script runs, and a `<noscript>` note that the chooser needs JavaScript. Without
  JavaScript the page MUST behave as in features 008 and 011.
- **FR-010**: Per layer the chooser MUST show one legend row per class: stud swatch, range in the
  layer's units (data) or role (background), BrickLink and LEGO color names, L*, share of the
  layer's studs.
- **FR-011**: Color pickers MUST offer only the colors cited for the layer's part
  (`part_colors.json` via `cells.json`), sorted light to dark by L*, with kit colors marked.
- **FR-012**: For `bins`, `rank`, `rank-to-supply` and `quantile` data layers the chooser MUST let
  the visitor set 1–12 classes and edit the class bounds (strictly increasing numbers); invalid
  input MUST be refused with a message next to the field.
- **FR-013**: The default state MUST reproduce the built preview exactly; changing colors only
  keeps the built classes; changing classes or bounds classifies the layer's cell values as bins
  (membership [lower, upper), values below the first bound in the first class, above the last in
  the last) and the page MUST say that custom bounds have no blend texture.
- **FR-014**: The chooser MUST offer a shadow color picker (tile colors) on maps with a land shadow.
- **FR-015**: The ice toggle MUST switch every land-ice and sea-ice cell (not the shadow) between
  the built/classified color and White, and class shares MUST count only cells that show data.
- **FR-016**: The chooser MUST state, per data layer, how many cells have no source value and how
  many of them are ice cells, and that they show the nearest value as in the build.
- **FR-017**: "Reset to the map's colors" MUST restore the default state and the built preview.
- **FR-018**: The chooser state MUST be encoded in the URL fragment and restored from it when
  valid for the page; the script MUST NOT set cookies, use browser storage, or contact any host
  other than the site.
- **FR-019**: The chooser MUST state "Preview only: parts lists, prices, build sheets and
  downloads use the map's default colors." and MUST NOT change any download link, parts table or
  price.
- **FR-020** (amends 008 FR-009): Pages MUST work without JavaScript, set no cookies, and load
  nothing from third parties (no trackers, analytics, fonts or scripts from other sites). The only
  script allowed is the site's own hand-written `/static/palette.js`, loaded with `defer` on map
  pages; there is no inline script and no front-end build.
- **FR-021**: Controls MUST be keyboard usable and labelled (fieldsets with legends for groups,
  labels for every input and select), the updated preview MUST have a text alternative, changes
  MUST be announced politely, and the layout MUST work at 360 px.
- **FR-022**: The About page MUST mention the chooser, that it is a preview only, and how the ice
  regions are defined.

### Key Entities

- **Map cells** (`cells.json`): per-variant data from FR-001.
- **Ice regions**: land-ice and sea-ice cells in kit coordinates with their rules and sources.
- **Chooser state**: per layer the colors and (for custom bins) the bounds; the shadow color; the
  ice toggle. Lives in the page and the URL fragment only.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: For every variant, the chooser's default rendering equals the built preview stud for
  stud (checked by recomputing the default colors from `cells.json` against `layout.json`).
- **SC-002**: A palette change re-renders the preview in under 100 ms on a laptop (10,240 studs).
- **SC-003**: The script is under 30 kB, hand-written, and the only script on the site.
- **SC-004**: With JavaScript off, every feature 008 and 011 page check still passes.
- **SC-005**: `cells.json` is under 300 kB per variant.
- **SC-006**: All CLI and web tests pass offline.

## Assumptions

- Visitors use a current browser with canvas support; without it the built preview stays.
- The chooser offers no download of the custom preview, parts or prices (owner: preview only).
- Values are rounded in `cells.json` to 0.01 for fields whose largest magnitude is below 100 and to
  whole units otherwise; class boundaries in the chooser use the same rounding.
- Out of scope: re-pricing, custom parts lists or build sheets, new datasets, uploads, browser
  storage, server-side state.
